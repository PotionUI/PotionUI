# MiniMax-H3

MiniMax-H3 (`src/platform/runtime/native/arch/minimax_h3/model.py`) generates a video track and its soundtrack jointly: video rows, text rows and audio rows are concatenated into **one** sequence that every block attends over, so there is no cross-attention and no separate audio pass. It is guidance-distilled — no CFG, no negative prompt, one forward per step — and runs flow matching with a reversed velocity sign and the timestep fed as `1 - sigma`.

The two streams do not share a noise schedule. Video and audio step the same number of times, but on independently shifted sigma grids (12.0 and 3.0), and the per-row timestep vector built for each forward is what lets one transformer call serve both. Both shifts are applied to **one** underlying `t` grid, so at every knot the two sigmas are two images of the same `t` — which is what keeps the pair packable into a single forward under any scheduler.

A step is one model evaluation (an NFE). `steps = N` puts `N` knots on the unshifted grid at `q_i = (N - i)/N` plus the terminal `0`, matching ModelTC's published turbo schedules: `steps = 4` gives video `[1, 0.973, 0.923, 0.8] → 0` and audio `[1, 0.9, 0.75, 0.5] → 0`. The Advanced tab's manual sigma boxes are the one place the other convention applies — those spell out the grid itself, so an `N`-value list runs `N - 1` steps.

## Files & detection

Every component is its own file — the DiT, the text encoder, the video VAE and the audio VAE are four separate downloads and four separate pickers in a preset. Detection keys on the DiT's structural signature (`video_patch_proj` + `audio_patch_proj` + `condition_proj` + fused `blocks.0.attn.qkv_proj`), and the same `ModelSpec` covers both checkpoint shapes: the **full** 33B checkpoint with a timestep-embedder MLP and full per-block AdaLN projections, and the **pruned** 20B one where that whole branch collapses to a 1025-entry lookup table and a rank-8 factorization.

What detection cannot see is the difference between the `fl2va` and `ref2va` checkpoints: they are architecturally byte-identical, same keys, same config. Only the file you pick decides which one runs, and picking the wrong one produces a silently wrong generation rather than an error.

The text encoder is the trimmed Qwen3-VL-32B repack — 50 decoder layers, no final norm, no LM head. H3's encode contract is the raw prompt with no chat template, no system prompt and no special tokens, tapped after layer 49; keyframe images enter the same sequence as vision blocks labelled `<Picture i>: `.

## Presets & modes

`content/presets/marketplace/MiniMax-H3` ships three modes. `video` covers both `t2va` (prompt only) and `fl2va` (optional first-frame and last-frame anchors); `refs` covers `ref2va`, conditioning on a set of references instead of keyframes; `upscale` is a standalone latent-space upscale + refine of an existing H3 video (see "Latent upscale" below). The same checkpoint architecture and the same generator pipe handle `video`/`refs` — but `ref2va` and `fl2va` are different *partitions* of the weights, so the `refs` mode needs the `ref2va` DiT file and the `video` mode the `fl2va` one, and nothing can detect a wrong pick.

### The `refs` mode (`ref2va`)

One References field takes up to 9 reference images, 3 videos and 3 audio tracks, 12 in total, and at least one reference of some kind. An audio reference cannot be the only kind — a soundtrack conditions a video that some visual reference has to anchor. Each modality contributes differently: an image contributes one visual condition latent at its own size, never enlarged and brought down to a 2048 px short edge by default when it is larger (the generator's `reference_short_edge`, which a mode can lower), and a picture outside 1:4 to 4:1, such as a tightly cropped full-body cutout, is padded symmetrically with white out to the nearer limit instead of being rejected, for the text encoder's copy as well as the generator's; a video contributes one visual condition latent as a whole frame stack (so `5n + 2` latent frames rather than 1), brought down to the canvas its own aspect ratio resolves to when it is larger, never enlarged, and truncated to the generated clip's length; an audio track contributes clean condition rows through the audio VAE and no picture at all. Each axis of a reference image or video lands on the 32 px grid at or below its own size once padded, so 1920×1080 encodes at 1920×1056, and only a source under one 32 px tile grows, to that one tile. A voice that is not at 32 kHz, or in a file `soundfile` cannot read such as a `.m4a`, is decoded and resampled through ffmpeg; a 32 kHz file `soundfile` reads keeps its own samples.

The references are **one packed sequence**, in a fixed order: every image, then every video, then every audio track. That order is what fixes each reference's label (`<Picture i>: `, `<Video k>: `, `<Audio j>: `, numbered per modality by the text encoder itself) and its position on the packed rotary clock. Three separate traversals have to agree on it — the encoder's presentation, the generator's reference blocks, and the condition-latent iterators the layout consumes alongside them — and a disagreement between any two is silent: the request runs, the shapes line up, and every reference conditions the generation from another reference's position. Both consumers therefore derive their traversal from one function (`pipes/_shared/generation/reference_order.py`), and each modality is loaded by exactly one media-loader node that both read.

In the Video Director (`refs` mode's `per_shot` capability), a shot's references are the ones its own prompt cites through `@[field:item]` resource markers — there is no separate per-shot selection. The normalizer turns the cited items into the shot's `reference_indices` (pool order: images, then videos, then audio) and rewrites each marker to a token numbered within that subset, so a shot citing the third and first images reads `<Picture 2>`/`<Picture 1>` against the two images it is actually conditioned on. Rows of a plugin picker mapped to a prompt resource source are cited the same way: citing one gives the shot every member and copy of that row, labelled after the shot's native references of each kind, and a row no shot cites conditions nothing in a Director run. A shot that cites nothing runs as a plain text-to-video window inside the same run, and a shot citing only audio is refused for the same reason as above. The References tab on each shot is a read-only overview of what the prompt cites, with an insert action for the rest of the pool.

`mode: "references"` on the generator is what makes an empty reference set an error rather than a text-only run: on the reference partition that fallback returns plausible video that ignores the request.

### Pre-encoded references

A pipe can feed references that are already VAE-encoded through the `reference_latents` input on both `generator/video_minimax_h3` and `prompt_encoder`. Each value is a `PreEncodedReference` (`src.plugin_api.pipes`): `kind` (`"image"`, `"video"` or `"audio"`), `latent`, `name` and `fingerprint`. The latent is in the VAE's raw, un-normalized space: `[1, 24, t, h, w]` for an image or video, `[2, 32, T]` for audio. The generator normalizes it with every other reference, and the prompt encoder decodes an image or video one through its `vae` input so the text encoder can see it. An audio one gets only its `<Audio j>: ` label.

Pre-encoded references are packed after every native reference of their own kind, in the order they arrive. Several providers wired to the same input are concatenated in edge order. The labels, the generator's reference blocks, Director `reference_indices` and the prompt encoder's `reference_selections` all index that one packed order. They count toward the per-kind and total reference limits, and one on its own satisfies `mode: "references"`. The prompt encoder's conditioning cache keys each one by its `fingerprint`, not by its tensor, so a provider must change the fingerprint whenever the latent changes.

### Plugin references

A plugin can add its own reference picker to the `refs` mode through a [preset extension](../presets/plugins.md#extending-existing-modes): a field on the References tab, a pipe that turns the picked rows into `PreEncodedReference` values for the `reference_latents` inputs above, and a [prompt resource source](../plugin-api.md#contributing-a-prompt-resource-source) so the prompt and the Video Director can cite each row's members. Without such a plugin the mode conditions on its native references only.

A keyframe is used twice. It goes through the text encoder's vision tower, so it appears in the prompt presentation as a `<Picture i>: ` block; and it is VAE-encoded into condition rows prepended to the packed sequence and pinned to a fixed timestep, rather than blended into the target latent behind a mask the way LTX conditions. Both consumers read one media-loader node in the preset, so they cannot disagree about which images they got or in what order. The keyframes are a fixed set shared by every output of a request rather than one source image per output, which the clip adapter signals with `forwards_full_image_batch` so `prompt_encoder` forwards the whole list to each request instead of indexing into it.

Every mode's Generation tab starts with a speed profile picker, then seed, quantity and the mode's size or length controls; a mode's inputs sit on its References tab, and steps, sampler and scheduler sit on its Advanced tab. There is no guidance scale and no negative prompt to expose, and audio has no toggle because it is inherent to the checkpoint — but the solver and the knot placement are independent of guidance, so both are offered.

### Latent upscale

Two entry points share one mechanism: a dedicated 3D latent upsampler checkpoint (`latent_upscaler/minimax_h3`, weights from `LBH-123-AI/Minimax_h3_latent_Upscaler` on Hugging Face, Apache-2.0 — a community-trained model, not a MiniMax first-party release) resizes an H3 video latent spatially, and `generator/video_minimax_h3` refines the result through its `initial_latent`/`denoise` refine entry path (see "Sampling" above) instead of starting from pure noise.

- **Standalone `upscale` mode.** Takes an existing H3 video (a `video`/`refs`-mode output, or anything else) and runs it through the full latent-space upscale + refine pass. `latent_upscaler/minimax_h3` VAE-encodes the source onto the release canvas for its aspect ratio, pads the frame count up to the video VAE's `17n + 5` lattice, then upsamples the resulting latent. Default recipe: target ≈2.1 decimal-megapixel area (1920×1088 for a 16:9 source), 4 refine steps, denoise 0.45, video stream sigma shift 9.
- **In-flow two-stage upscale (`video` mode's Enhance tab).** Stage 1 generates at the picked Resolution without decoding (`decode: false`); `latent_upscaler/minimax_h3` upsamples that raw latent directly, no VAE round trip; stage 2 refines the upsampled latent and decodes. Default recipe: 4 refine steps, denoise 0.45, video stream sigma shift 9 — the same recipe as the standalone mode. A first/last frame or Video Director document still shapes stage 1's generation, but is not re-applied at stage 2: `generator/video_minimax_h3`'s refine entry path is mutually exclusive with keyframe/reference conditioning (unlike LTX-2's own two-stage upscale, which re-encodes keyframes at the refined resolution) — whatever identity stage 1 established is already baked into the latent stage 2 refines.

Both entry points share the same refine knobs: a `refine_denoise` select (Light 0.30 / Balanced 0.45, default / Strong 0.60; References tab in `upscale`, Enhance tab in `video`), `refine_video_sigma_shift` (default 9, Advanced tab; the audio stream's own shift stays fixed at 3.0 and is not exposed for a refine), a step count, `refine_sampler`, and `audio_refine` (Advanced tab, default Lock). The step count is the Enhance tab's `refine_steps` in `video`; in `upscale` it is the Advanced tab's `steps`, driven by the speed profile like every other mode, with Custom as the default so the 4-step recipe stays editable. `cfg` is not a knob here as elsewhere in this family — H3 is guidance-distilled and the generator pipe has none.

A refine's target audio rows are never plain noise: pure noise cannot become audio in a 4-8 step low-sigma refine, and those rows share the packed sequence the video rows attend to every step, so leaving them unconditioned showed up as noise/artifacts in the refined *video* too, not just a bad soundtrack. `audio_refine: "lock"` (default) seeds the audio rows from the prior stage's own audio latent, noised to a fixed near-clean timestep and held there for every step — excluded from the per-step update the way the packed sequence's condition rows already are, a third fixed-timestep row category alongside them. `"resample"` instead noises that same seed to the refine's own truncated audio schedule and lets it sample normally, the way stage 2 already treats video. The in-flow path wires stage 1's `audio_latent` output straight into stage 2's `initial_audio_latent`, no VAE round trip; the standalone `upscale` mode has no earlier stage to draw one from, so it encodes the source clip's own track through the audio VAE instead (the same track `audio_source: "passthrough"` mux'es into the final output). A refine with neither a stage-1 latent nor a passthrough track to encode is refused outright rather than sampling the audio stream from unconditioned noise.

The FINAL muxed track is a separate choice from all of the above: both entry points keep `audio_source: "passthrough"`, which mutes the refine's own decoded/sampled soundtrack and mux'es the *source* track verbatim — the standalone mode's own input video, or (in-flow) stage 1's own decoded/generated `audio` output passed into stage 2's `audio` input — so a Generate Audio request or a Director-supplied track both survive the refine's mux unchanged regardless of what `audio_refine` did during sampling.

**Stage-2-only LoRAs (Enhance tab's `refine_loras`).** Stage 1 and stage 2 each get their own exclusive LoRA set — e.g. a fast distillation LoRA for the refine while stage 1 keeps rendering the base model, undistilled, at its own step count — without a second DiT load. `model_loader/minimax_h3`'s own DiT fingerprint folds the LoRA stack's fingerprint in (`vdn.dit_fingerprint`), so baking two different LoRA sets into two acquisitions under the same cache key would evict and reload the ~20-40GB DiT from disk between stages, and again on the next generation (`ModelLifecycle.acquire`'s fingerprint-mismatch path always calls the loader fresh — there is no cheaper partial-reuse path for a baked LoRA change). Instead, the ONE `model_loader/minimax_h3` node bakes NO LoRAs (`loras: []`) once Latent Upscale is on, and `generator/video_minimax_h3`'s `runtime_loras` config applies a LoRA stack around that call's own sampling only: `snapshot_lora_state` + `apply_loras` patch each `Linear` BEFORE `place_dit_for_sequence` sizes and places the DiT (so the placement budget already includes the patched weights), then `restore_lora_state` after sampling — generator_stage1 applies the LoRA tab's `loras`, generator_stage2 applies `refine_loras`, both against the SAME resident DiT, one load, no reload between stages or between generations. `runtime_loras` is a generic primitive, not refine-only: it works identically on a plain from-noise call. The standalone `upscale` mode's own `refine_loras` (LoRA tab) still bakes at load time as before — it has only ONE generator call, so there is no second acquisition to avoid.

Run the refine without the turbo LoRA unless its strength is set for the missing alpha (see "The original turbo LoRA is missing its alpha metadata" under Limitations below) — neither entry point requires it, and this repository's own recipes are validated LoRA-free. GPU validation for this feature is pending, same as the rest of the family. A ~2.1MP target over many frames makes the refine pass VRAM-heavy — for long clips, pair it with `sparse_attn: sla` and the SLA turbo LoRA (see "Sampling" above) rather than running it dense.

## Sampling

Default generation parameters: 24 steps, 1344×768, 124 frames at a fixed 24 fps (≈5.2 s).

The preset offers three named speed profiles plus `custom`. `quality` and `turbo` carry a step count and nothing else — being guidance-distilled, the family has no guidance for a profile to switch, and the sampler and scheduler are left to the user. `quality` is 24 steps; `turbo` is 4 steps. `flex` is 6 steps and pins the sampler and both sigma grids too; see "Pika H3 Flex" below.

Five deterministic and stochastic solvers are available (`euler`, `res_multistep`, `dpmpp_2m`, `er_sde`, `sa_solver`), plus `lcm`, all stepping in `x0` space off the same data estimate. The first three are described here. `euler` is the reference solver and the default, and it is what the turbo LoRA was distilled against. `res_multistep` (second-order exponential Adams–Bashforth, derived from the exponential-integrator form rather than ported) and `dpmpp_2m` (DPM-Solver++(2M), adapted from the MIT-licensed `vendor/k_diffusion`) both reuse the previous step's estimate, so they cost no extra forward and buy accuracy where the grid is coarse — most visibly at turbo step counts. Their history is per stream and per window: video and audio walk different sigma grids inside one forward, and each window is an independent trajectory whose first step legitimately has no past.

Three schedulers place the knots. `simple` is the reference uniform grid; `beta` pushes the same uniform quantiles through a Beta(0.6, 0.6) quantile function, which clusters knots at both ends — more steps on early composition and on final detail, fewer in the middle. `beta57` is the RES4LYF recipe of the same name, ComfyUI's beta scheduler at Beta(0.5, 0.7): it leans the knots toward the clean end. As in ComfyUI, the quantiles space the unshifted `t` grid and each stream's shift is applied on top; at 8 steps the unshifted knots are `[1, 0.889, 0.719, 0.536, 0.361, 0.211, 0.096, 0.024] → 0`.

Each stream's shift is its own Advanced-tab field: Video shift (`video_sigma_shift`, default 12) and Audio shift (`audio_sigma_shift`, default 3), the released checkpoint's values. Both are hidden under `flex`, which pins its own grids, and both are ignored while a manual sigma grid is set. The community 8-step recipe — `custom` profile, 8 steps, `euler`, `beta57`, shifts 12/3, no LoRA — runs from these fields alone; no named profile carries it. A manual sigma grid together with a non-`simple` scheduler is refused rather than resolved by precedence: both knobs answer the same question, and a silent winner would leave the scheduler picker reading as if it did something on a run it has no say in.

`turbo` needs no LoRA. The base model is a capable three-to-four-step generator on its own shift-12 schedule, producing usable output with softer detail than a 24-step run rather than the noise a few-step run on an undistilled model would normally give. The turbo distillation LoRA sharpens it further, but it is an option, not a prerequisite.

Two further speed levers ship off by default. The `video` mode's Advanced tab carries a pixel-budget cap that bounds how large a keyframe the text encoder's vision tower reads (as a multiple of the output canvas area — keyframes otherwise enter at up to their full 16.7-megapixel processor bound, which the 32B encoder pays for directly); and the advanced tab carries the same First Block Cache knobs as the other video families (`step_cache_threshold` and friends), wired into this family's bespoke dual-schedule loop so a skipped step reuses both streams' velocity in one decision. A replayed velocity enters a multistep sampler's history unchanged — it is the model's most recent real output, and the sample it applies to did move — so caching and a second-order sampler compound: cache more conservatively (a lower `step_cache_max_skips`) when running `res_multistep` or `dpmpp_2m`. Neither lever has been speed- or quality-measured on real H3 weights yet.

A third lever, also off by default, is **sparse attention** (advanced tab: `sparse_attn`, one method select — `off` / `sol` / `sla` — plus each method's own knobs). Both methods are approximations of attention, not a cheaper way to compute the same numbers, and both compose with the step cache — a cached skip never reaches attention at all.

**Sol-Attn** (`sparse_attn: sol`, tuned with `sol_attn_tau`) summarises every 128-token KV block by its mean vector, scores those summaries against pooled query blocks, and computes exact attention only over the blocks that clear a threshold plus the always-exact local diagonal window. The implementation is vendored from [ComfyUI_sol-attn_Blackwell](https://github.com/KingGore/ComfyUI_sol-attn_Blackwell) (Apache-2.0) at `vendor/sol_attn/`; upstream measured its speedups on an RTX 5090 (sm120) and this engine allows it on any bfloat16 CUDA device of compute capability 8.0+, unmeasured elsewhere.

**SLA** (`sparse_attn: sla`, tuned with `sla_sparsity` and `sla_block_size`) instead mean-pools every KV block and every query block, scores the pooled pairs with one matmul, and keeps only the top-k fraction of key blocks per query block — a fixed sparsity budget rather than a threshold. It pairs with the LightX2V SLA turbo LoRA, distilled against ~85% sparsity, so `sla_sparsity` 0.85-0.90 is the sensible range once that LoRA is loaded; below roughly 0.60 SLA is slower than dense attention, not faster. `sla_block_size` defaults to 64, the audio-safe choice — 128 forces roughly 1.6s of audio through one attention pattern and made speech robotic in upstream testing. The implementation is vendored at `vendor/sla_attn/` (Apache-2.0 over MIT), a single Triton kernel with no CPU/non-CUDA fallback backend the way Sol-Attn has a second implementation.

Both methods pin the packed sequence's whole prefix (text, condition audio, keyframe conditioning and the target audio rows) so every query still attends to it exactly, and both run the last `sparse_attn_dense_last_steps` steps of every window (2 by default) on the ordinary dense path — the end of a trajectory carries the least noise to hide a sparse approximation behind. Anywhere a method cannot run — no CUDA, wrong dtype, a torch whose `flex_attention` fails (Sol-Attn) or no usable `triton` (SLA) — it logs one warning naming the reason and the generation continues on the normal attention path at normal speed and quality. Neither method has been speed- or quality-measured on real H3 weights yet.

Choosing between them: Sol-Attn is the threshold-routing method to A/B against dense attention at an arbitrary step count. SLA is the one to reach for on a 4-step Turbo run paired with the SLA turbo LoRA, and it needs far less transient VRAM to get there.

Neither method is free in VRAM, but the cost differs sharply between them. Sol-Attn's routing pass materialises the packed q/k/v several times over — padded to a multiple of 128, then permuted contiguous to head-major — so at 768×1344 / 141 frames (43k rows, 56 heads) one such copy is 590 MiB and the peak holds roughly eight of them, about 5.3 GB on top of the ordinary activation reserve. SLA's routing works in pooled block space instead of full-size copies, so the same 43k-row sequence reserves well under 1.5 GB. The generator estimates each with its own `estimate_transient_gb` and passes the result to `place_dit_for_sequence` as `reserve_gb`, so the placement holds the room back before deciding how much of the DiT stays resident; with the feature off the reserve is 0.0 and placement is unchanged. Sol-Attn's first real run without this reserve OOM'd mid-sampling (a 590 MiB allocation with 151 MiB free) and fell back to dense attention as designed. Expect enabling Sol-Attn on a 32 GB card to push the DiT further into partial residency — whether the cheaper attention pays for the extra weight streaming is exactly what an A/B on real weights has to answer; SLA's much smaller reserve makes that tradeoff far less likely to bite.

The live preview decoder (`taeh3`) is held back separately as `preview_reserve_gb`: its fp16 weights (0.021 GB) plus one preview decode. For a 124-frame 768×1344 clip that is 0.557 GB, so `weight_budget_gb` goes down by that much. Before this reserve, the extra VRAM the preview held after a clip decode left the first dense step after SLA 576 MiB free for a 532 MiB LoRA allocation, and that step OOM'd. The formula is in `docs/native-engine.md` under *Sequence-length activation reserve*.

Geometry is constrained on both axes. The canvas must be a multiple of 32 with an aspect ratio between 1:4 and 4:1, and the generator rejects anything else instead of snapping it — the released canvas is 1344×768 (short edge 768, area capped at 768·1344), and smaller canvases are the family's strongest speed lever (960×544 runs roughly 2.3× faster per step). The frame count *is* snapped, upward to the next `17n + 5` the video VAE can decode, which maps to `5n + 2` latent frames; the audio stream's length follows from it at 40 latents per second per channel, doubled for stereo. Clips run up to 15 seconds — the model's release notes suggest staying at 5s or above, but that is a recommendation, not a limit this engine enforces; the real floor is whatever the `17n + 5` lattice accepts (as low as 5 frames).

Sampling draws three noise tensors from one generator per seed, in a fixed order — conditioning, then video, then audio. Reproducing a seed elsewhere requires that same order.

## VDN (experimental)

Video DeltaNet ([OpenVDN/vdn-minimax-h3](https://huggingface.co/OpenVDN/vdn-minimax-h3), code Apache-2.0) adds a **second attention branch** to every one of the 50 blocks. The original attention is narrowed to a local window of frames — chunk 5, radius 1, plus the first and last frame dense in both directions, plus every text, audio and condition row as a dense global — and a bidirectional gated-delta-rule recurrence over frames supplies exactly what that window cannot see. The two sum. The block's fused `qkv_proj` is **shared** between them, so the branch adds no projection cost, only its own post-processing, scan and output projection. The window and the recurrence are trained-in: `radius`/`chunk` are ablation knobs upstream, not inference settings, and a port should treat 5/1 as fixed. It ships as `content/presets/marketplace/MiniMax-H3-VDN`, alongside the unmodified base preset.

Three files, all under `stage-dmd-step-250/` in that repo, all published under generic names that need renaming on download:

| File | Bytes | What it is |
|---|---:|---|
| `linear_branch/model.safetensors` | 4,279,428,112 | The branch itself: 50 blocks × 16 tensors, 2.14B parameters. 90% of it is one `[5376, 7168]` output projection per block, which the ordinary quantized-Linear and streaming-prefetch machinery handles like any other projection. Byte-identical to the copy under `stage-b-step-2000/`. |
| `adapters/default/adapter_model.safetensors` | 334,026,912 | Rank-64 LoRA on the attention projections and the token refiner. Required on every render. |
| `adapters/turbo/adapter_model.safetensors` | 851,452,696 | The 8-step DMD distillation, 363 explicit targets. Only for the 8-step tier. |

Both adapters are PEFT diffusers-dialect with **alpha equal to rank**, so the merge scale is exactly 1.0 and the preset's LoRA field takes them at strength 1.0 — unlike the base family's turbo LoRA, which needs a hand-set 0.125. They merge additively in `sorted()` order, `default` then `turbo`, which is the order the preset's LoRA list has to carry. The 8-step tier is **not** self-contained: `stage-dmd-step-250`'s branch and default adapter are byte-identical to `stage-b-step-2000`'s, so the DMD stage is stage-b plus one further adapter and there is no shortcut past porting the whole branch.

Two tiers, and only two: **8 steps** with both adapters, **50 steps** with the default adapter alone. Shifts are unchanged (12.0 video, 3.0 audio) and a distilled adapter is only valid at the shifts and step count it was trained for, so the base preset's 24/4 profiles do not carry over. There is no guidance here either — one forward per step, no negative branch, no per-step LoRA scaling and no special first/last-step handling.

**The AdaLN sidecar.** The turbo adapter targets `transformer_blocks.N.adaln_proj.linear` with `lora_A` of shape `[16, 2688]`. That `2688` is the **full** checkpoint's `time_embed_dim`. The pruned repacks — every Comfy-Org H3 file — replaced the timestep-embedder MLP with a 1025-row lookup table and a rank-8 factorization whose input axis is 8, and there is no linear map between the two bases: the two checkpoints compute AdaLN differently on purpose, down to `apply_silu`. Applying the adapter over a pruned checkpoint is therefore impossible as published, and dropping those rows silently would change the distillation the adapter encodes. The preset's answer is a **sidecar**: a ~63 MB safetensors carrying the full checkpoint's four `time_embedder.*` tensors, produced by `python scripts/h3_extract_time_embedder.py` and selected in the preset's *AdaLN sidecar* picker. It is required only when the DiT is a pruned repack **and** the turbo adapter is loaded; the 50-step tier and full 33B checkpoints need nothing.

**Memory has an unusual shape.** The branch's transient working set scales as `F·H·d²` — frames, heads and head dimension — and is **independent of spatial resolution**. At the released 768p/102-latent-frame geometry it peaks around 4.3 GB while a block runs (the scan's transition, injection, prefix, suffix and state banks, plus the readout), released before the next block, on top of the 4.28 GB the branch weights hold for the whole render. Halving the canvas does not reduce it; halving the clip length does. That is the opposite of the advisory's usual assumption and worth modelling explicitly rather than by analogy to dense attention.

Limitations, all of them structural rather than provisional:

- **Sparse attention is mutually exclusive with the branch.** Sol-Attn and SLA sparsify the *same* dense attention the VDN window already restricts; both decide which key blocks a query sees. The VDN preset offers neither.
- **Low-VRAM sequence chunking (`seq_chunk_rows`) is out.** The branch needs all `F·S` video rows at once for the frame statistics and the scan. The default MLP chunking still runs: the MLP is per-row and never sees the window.
- **Keyframes are untrained.** OpenVDN's render path builds its packed sequence with `keyframe_anchors=()` — t2va only — so no published VDN checkpoint has seen a keyframe-conditioning row. The rows map correctly (target video rows are the contiguous t-major block at the end of the sequence, and condition rows fall into the window's dense globals), but the base family's primary mode is fl2va, which makes this a first-class question rather than an edge case. The preset declares `i2v`/`flf`/`director` anyway and says so at every point a user meets one.
- **One geometry has evidence.** `LATENT_H`/`LATENT_W` are module constants upstream, pinned at 768p; the arithmetic is geometry-agnostic but the weights were neither trained nor evaluated anywhere else.
- **A naive masked attention call is slower than dense.** The window has to be expressed as gathered dense calls or a block-sparse kernel; an `attn_mask=` SDPA call materialises a `56 × 105k²` mask. OpenVDN's own 2.9× headline is an H200 with FlashAttention-4, fp8 and every fused kernel, so the honest local framing is long-clip feasibility, not a speedup.
- **GPU validation is pending**, as for the rest of this family. Nothing above has been run.

Licensing is unchanged and covers the variant: OpenVDN's code is Apache-2.0, but the weights it redistributes and the branch and adapters trained on top of them are under the MiniMax H3 Community License, with the same territorial exclusion (EU, UK, US, South Korea) reaching the outputs as well as the weights.

## Fun ControlNet (control video)

The DiT can carry Alibaba PAI's MiniMax-H3 Fun ControlNet Union as a model patch, loaded by `model_loader/minimax_h3` through its `control_module` setting and fed by the generator's `control_video` input. A control video (a DWPose skeleton, depth, canny, HED, MLSD, scribble, layout or gray render) steers the movement and layout of the generated video while the soundtrack still follows the prompt: the patch never reaches the audio rows.

**Files.** Only the pruned Comfy-Org repack fits a pruned DiT: `minimax_h3_fun_controlnet_union_2.0_pruned_bf16.safetensors` (8.4 GB) or `..._pruned_int8_convrot.safetensors` (4.5 GB), both under `model_patches/` in `Comfy-Org/MiniMax-H3`, plus the older 5-block v1 pair. Their AdaLN projections are rank-8 bases that read the pruned DiT's own timestep curve. Alibaba's original file needs the 33B full DiT's `time_embedder` and is refused with a pointer to the pruned patch. Detection is by block count (5 = v1, 10 = 2.0) and the file's `control_blocks_places` / `inpaint_masked_pixel_mode` metadata; a count, places or pixel-mode mismatch is rejected rather than loaded.

**How it runs.** A parallel stack of control blocks (one per injection layer: `0,5,...,45` for 2.0, `0,10,...,40` for v1) runs over the same packed sequence, with the control latents in place of the generated video rows. Each control block's output goes through a zero-gated projection and is added to the main block at its layer. The control stack is interleaved with the main stack, so only one hint is alive at a time and a first-block-cache skip also skips the remaining control blocks. Control blocks always use dense attention.

**Rows.** `control_hint_rows="trained"` (default) adds hints to the text and generated video rows, the rows the branch was trained on. `"non_audio"` also adds them to keyframe and reference rows. Audio rows never get hints. The branch was trained on text-to-video only, so combining it with a first-frame keyframe or `ref2va` references is supported but not validated upstream.

**Length and canvas.** The clip follows the control video: its frames at 24 fps, snapped down to `17n + 5`, at most 15 s; `resolution: auto` takes the canvas aspect from it. `control_length_from_video: false` keeps `frames` instead. The control video is encoded once per request with the posterior mode, and its rows are zero-padded over the inpaint columns (motion transfer needs no mask).

**Strength.** `control_context_scale` is 1.0 upstream (strongest), lower follows the control loosely, 0 switches the branch off bit-exactly. `control_start` / `control_end` limit the steps (as a fraction of the sampling) on which the hints are added. Upstream samples at 40 steps with guidance 1; whether the Turbo and FastH3 step counts hold is not established.

## Motion transfer

The `motion_transfer` mode takes a picture of a person and a video of someone moving, and the person from the picture performs the moves. The look, clothes and background come from the picture; only the movement comes from the video.

The pipeline is `media_loader` (video) and `media_loader` (picture) → `control_video` → `model_loader/minimax_h3` with the control patch → `prompt_encoder` → `generator/video_minimax_h3` → `gallery`.

- `control_video` (`type: pose`, see [Pose guide](../pose-guide.md)) renders a whole-body skeleton guide. With the picture wired in (`match_picture`) the skeleton is retargeted onto the person in the picture, so the guide is drawn in the picture's own frame and the canvas follows the picture, never the video. `size_multiple` is 32 and `max_pixels` is H3's own canvas budget, so `resolution: auto` lands on the picture's aspect on the 768 short edge. `ease_in` (Advanced, default 0.5 s) blends from the picture's pose into the video's moves, so frame 0 agrees with the first-frame keyframe. `save_guide` also saves the skeleton video to the gallery.
- The guide is the generator's `control_video`. The DiT is the fl2va file plus the Control model field, a pruned Fun ControlNet Union 2.0 patch loaded as `control_module`: int8 ConvRot (4.5 GB) is the pick for a 32 GB card, bf16 (8.4 GB) the alternative. "Follow strength" is `control_context_scale`.
- The picture is the first-frame keyframe (`keyframe_anchors: [first]`) and the prompt encoder reads it as `<Picture 1>`. This identity path is provisional. The alternative is ref2va, with the picture as a reference and `<Subject 1>` defined by `<Picture 1>`. The preset var `motion_identity` in `preset.yml` picks between them: `first_frame` (default) or `reference`. The reference path needs the ref2va DiT in the Model picker; nothing detects a wrong pick.
- The length follows the guide: its frames at 24 fps snapped down to `17n + 5`, at most 15 s (`control_length_from_video`). The guide renders at most 15 seconds of the source (`max_seconds: 15`, whatever its frame rate), so pose detection never runs on frames the generator drops.
- Sound is Generate (new sound from the model, the default) or Keep the video's sound (`audio_source: file` fed by the driving video).
- The mode defaults to the Quality speed profile (24 steps). Whether the Turbo step count holds with the control patch is not established, and the patch was trained on text-to-video only, so the keyframe combination is supported but unvalidated upstream.
- One person, front-facing and well lit works best. Crowds, motion blur and side profiles are where the pose reading fails.

## Long video

The `long` mode chains parts into one video of up to two minutes, with seamless joins. It is the existing Video Director window chain driven by a simple form, not a second mechanism: the preset builds a Director document from the form and records `settings.long` (`total_seconds`, `part_seconds`); `windows.py` derives each part's frame count from that (`long_video_parts`, also a template filter the preset uses only to count the parts), and `generator/video_minimax_h3` runs it.

**Inputs.** An optional Start picture (the first frame of the first part; empty starts from the prompt alone), the main Prompt, an optional Prompt per part (one line per part, in order; a part without a line uses the main prompt), Length in seconds, an optional Soundtrack, the resolution, the speed profile and the model files. `Part length` and `Colour hold` are on the Advanced tab. To continue an existing clip, use the `extend` mode.

**How the chain runs.** The length is cut into parts of Part length (rounded up to the model's `17n + 5` frame lattice, never over 15 s). The first part is text-to-video, or image-to-video from the Start picture. Every later part is a `chain` segment: the previous part's last 17 frames are re-encoded as keyframe condition rows at the head of the next window, the audio carries over as clean condition-audio rows, and the replayed overlap is trimmed so each part contributes only new footage. The last part is sized to what is left, and the stitched result is trimmed to Length. It is one request with one progress bar, one cancel, and one resident DiT.

**Why a window chain and not one generation per part.** The generator already owns continuation (the latent splice, the audio carry, the stitch, per-window seeds and prompts), and a request that drives it needs no new orchestration layer. Running each part as its own queued generation would reload or re-place the model per part, lose the audio carry, and make a cancel or a failure in part four leave three orphaned results.

**Colour hold.** Each continuation window is decoded to pixels and re-encoded to condition the next one, so small colour shifts compound across parts. `drift_correction` (default 0.5 in this mode, 0 elsewhere) matches each continuation window's per-channel mean and spread to the first window's, scaled by the strength, before the window joins the timeline and before its tail conditions the next window. The contrast correction is capped to 0.8x-1.25x. A hard cut (a segment that opens on its own image) starts a new anchor. Identity drift is not corrected: keep parts short (5-10 s) and describe the subject the same way in every part prompt.

**Sound.** The soundtrack, when given, is laid over the finished video in place of the generated sound. It does not drive lip-sync. The lip-sync chain would need the ref2va reference partition, whose Director windows are hard-cut-only here and take no per-window audio slice.

**Seeds.** A part's seed is the document seed plus its index. A Director document with no seed now takes the request's own seed (what the Seed field resolves to, random for -1) instead of counting up from -1, which made every such run identical; a document that carries a seed, as the Video Director's always does, is unchanged. A configured generator `seed` of 0 or more still wins.

**Unmeasured.** GPU validation of a 30-60 second chain, and of the default Colour hold, is pending.

## Perfect loop

The `loop` mode makes a clip whose last frame flows into its first with no seam, for animated wallpapers: a picture and a sentence about what moves go in. It is the generator's `loop` setting driven by a small form, and the technique page [Perfect Loop](../techniques/perfect-loop.md) has the mechanism and the frame arithmetic.

**Inputs.** An optional Start picture (the loop starts from it and returns to it), What moves (the prompt; the mode writes the three-field document itself and asks for a fixed camera, and a prompt that already is a full three-field document is used as written), Length in seconds (6 by default), Movement (Subtle by default, or Lively), Resolution (the family's standard picker, 1344x768 by default), Sound (off by default), the speed profile and the model files.

**How it runs.** Two windows in one request with one progress bar: an anchor pass (text-to-video, or image-to-video from the Start picture, fitted to the picked resolution once, keeping its aspect) and a bridge pass whose first 17 frames are pinned to the anchor's last full chunk and whose last 22 frames to the anchor's opening. The pins are the anchor's own latents, entered both as condition rows and as target rows held on the source's noised path, so the bridge's ends come back bit-identical. The loop is joined in latent space and decoded with one chunk of wrap-around context, so the seam decodes like any other chunk boundary. The bridge seed is the request seed plus one.

**Length.** Rounded to whole 17-frame chunks (0.71 s), at least two chunks, at most 26.9 s; with sound in 51-frame steps (2.125 s), at most 25.5 s. A longer request is refused in plain words.

**Sound.** Off writes the loop without a soundtrack (the stream is still sampled with the picture). On pins the bridge's audio the same way and decodes it with wrap-around context.

**Use the full step count.** Measured on real weights: Quality at 24 steps closes the loop. A 4-step run drifted and cut at the wrap. `tests/manual/h3_perfect_loop_check.py` measures a loop: jumps and resets (with the frame a reset jumps back to), stops, and zoom drift.

## Pika H3 Flex (6-step adapter)

[Pika-Labs/Pika-H3-Flex](https://huggingface.co/Pika-Labs/Pika-H3-Flex) is a pair of rank-128 LoRA adapters on the base DiT, one for the fl2va partition and one for the ref2va partition, post-trained with step distillation from 50 to 6 steps plus a quality finetune. It adds no conditioning and no architecture, so it runs through the same generator as every other profile.

**Where it appears.** A `Flex` choice in the Speed profile of `video`, `extend`, `refs`, `remix` and `talk`. `upscale`, `refine_faces` and `motion_transfer` do not offer it. `turbo` stays the default of the `video` mode. `MiniMax-H3-Fast` and `MiniMax-H3-VDN` have no Flex profile.

**Files.** A Flex adapter model field appears on the Models section when Flex is chosen. The recommended files are the Comfy-Org bf16 repacks in [Comfy-Org/MiniMax-H3](https://huggingface.co/Comfy-Org/MiniMax-H3) under `loras/`, 1.96 GB each: `pika_h3_flex_fl2va_v1_bf16.safetensors` (sha256 `cc5453ae...358b7`) for the first/last-frame modes (`video`, `extend`) and `pika_h3_flex_ref2va_v1_bf16.safetensors` (sha256 `de3745ce...b0e0`) for the reference modes (`refs`, `remix`, `talk`). Use the file that matches the mode's DiT; a mismatched pair loads cleanly and gives a worse video. The adapter keys are in the ComfyUI generic dialect (`diffusion_model.blocks.N.attn.qkv_proj.lora_A.weight`, q/k/v fused block-diagonally at rank 384, scale folded into `lora_B`, no `.alpha` keys), and the LoRA mapper reads them with zero unmatched keys at unit scale. The original FP32 PEFT files use the diffusers dialect the mapper already reads.

**Recipe.** Choosing Flex renders, in every mode that offers it:

- `steps: 6`, the Steps slider locked;
- `sampler: lcm`, `scheduler: simple`;
- `manual_sigmas: 1.0, 0.972973, 0.923077, 0.8, 0.571429, 0.333333, 0.0` (the base ladder 1000/750/500/250/100/40/0 pushed through shift 12) and `manual_audio_sigmas: 1.0, 0.9, 0.75, 0.5, 0.25, 0.111111, 0.0` (the same ladder through shift 3);
- the step cache off;
- the adapter in `runtime_loras` at strength 1.0.

The recipe lives in the `flex` entry of `speed_profiles:` in `preset.yml`, and the pipelines read it from there, so the sampler, sigma and step cache fields on the Advanced tab are hidden under Flex rather than left showing values that would not run. Euler at six steps, or only one of the two ladders, gives a plausible but worse video, which is why all of it is pinned together.

**`lcm`.** A sampler that predicts the clean sample `x0` and re-noises it with fresh seeded noise to the next sigma, `x_next = (1 - sigma_next) * x0 + sigma_next * noise`; the last step returns `x0`. It draws noise every step from the window's own generator, like `er_sde`. It needs a distilled adapter in `runtime_loras` and is refused otherwise, and it is refused on a DiT carrying a VDN branch.

**No reload.** The adapter is applied around sampling as a runtime LoRA, so switching between Quality, Turbo and Flex reuses the resident DiT and text encoder. It costs about 1.8 GiB of extra VRAM while applied.

**What it cannot be combined with.** Flex hides and ignores the LoRA tab, because the turbo distillation LoRAs are a second step distillation and stacking them over-distils the result. VDN and FastH3 are separate presets without a Flex profile. The Enhance tab's refine pass runs on the base model after a Flex first stage; the Flex ladders do not support a partial denoise, so the adapter is never applied to the refine. The Fun ControlNet patch was trained on the base model at 40 steps and `motion_transfer` does not offer Flex; stacking the two by hand with the Custom profile is experimental and unvalidated.

**Resolution.** The `video` and `refs` resolution lists carry Pika's eleven 480p buckets as a "480p (Flex-trained)" group, next to the native 768 canvas and the Faster list.

**Sound.** Sound comes only from explicit audio references, as for every other mode.

**Licence.** The adapters are Model Derivatives under the MiniMax H3 Community License, the same terms as the base weights described under Limitations. PotionUI ships no weights.

**Unmeasured.** The quality and speed against Turbo and Quality has not been A/B-tested on real weights.

## Limitations

- **The weights are territorially restricted.** MiniMax-H3's weights are published under the MiniMax H3 Community License, not an open-source license. Its Applicable Territory excludes the European Union, the United Kingdom, the United States and the Republic of Korea, and the exclusion extends to the model's outputs; use in those territories requires an individual authorization from MiniMax (https://platform.minimax.io/h3-license). The license additionally requires separate written authorization above US$20M annual revenue, and requires a commercial product's interface to display "MiniMax H3" prominently. PotionUI ships no H3 weights. The architecture implementation is ported from the Apache-2.0 diffusers source, which carries none of these terms.
- **The original turbo LoRA is missing its alpha metadata.** The ModelTC release of the 4-step distillation LoRA ships without the PEFT alpha its training used (alpha 16 at rank 128, so the intended scale is 0.125). Nothing in the file says so, which means any consumer applying it at face value — this engine and ComfyUI's generic default alike — runs it eight times too strong and gets noise at any step count. Two workarounds: use Kijai's conversion (`minimax_h3_fl2v_lightx2v_turbo_4step_v0.1_comfy.safetensors` in [Kijai/MiniMax-H3_comfy](https://huggingface.co/Kijai/MiniMax-H3_comfy)), which bakes the correct scale in and is right at roughly 0.75 strength, or keep the original and set its strength to 0.125 by hand. The preset's LoRA field points at the former in its `ai_hint`; it cannot offer it as a download, because `recommendations:` is a `model`-field feature that `lora_picker` does not serialize. Full derivation, including the bit-exact comparison that proved the factor, is in `ai/minimax_h3/TURBO_LORA_FINDINGS.md`.
- **A reference is never enlarged, unlike the released pipeline.** The released pipeline brings every reference image up to a 2048 px short edge and every reference video up to the canvas its aspect ratio resolves to. Here a smaller source stays at its own size on the 32 px grid, which shortens the packed sequence: an 832×480 image costs 390 condition tokens rather than 7,104. Because the request's noise is drawn after one draw per visual reference shaped like its latent, the same seed gives a different result than a run that enlarged the same reference.
- **A resampled voice does not go through the released pipeline's resampler.** The released pipeline resamples a soundtrack with `torchaudio`; here a voice off 32 kHz goes through ffmpeg's default resampler before it reaches the audio VAE. `normalize_condition_waveform` keeps the `torchaudio` route for any caller that hands it another rate.
- **A reference video's own soundtrack is ignored.** The released pipeline reads sound off a video reference that carries one; here a video reference conditions the picture only, and sound reaches the model exclusively through an explicit audio reference. The reason is that the two consumers decide independently: the text encoder emits `<Audio j>: ` for an audio-bearing reference, the generator packs the rows, and if a probe and a demux ever disagreed about whether a file has usable sound the presentation and the packed sequence would silently describe different references. Picking the audio track explicitly makes that impossible and puts the choice in the user's hands.
- **A reference video too short for two sampled frames is still presented.** The text encoder reads a reference video at 2 fps and merges the sampled frames in pairs. The released diffusers pipeline refuses a video that yields only one sampled frame (under 13 frames at 24 fps). Here the frame is paired with itself, as the Qwen3-VL video processor and ComfyUI's H3 text encoder do, and labelled `<0.0 seconds>`. This covers clips under about half a second and pre-encoded video references decoded from a few latent frames, such as a stack of two pictures.
- **`int8_convrot` is supported for the video VAE, untested for the DiT.** The quantized video VAE repack (`minimax_h3_video_vae_int8_convrot.safetensors` in [Kijai/MiniMax-H3-experimental](https://huggingface.co/Kijai/MiniMax-H3-experimental)) loads and decodes here: its 144 int8 ViT-decoder linears carry per-output-channel scales plus a ConvRot (Hadamard) rotation the engine un-rotates at dequant, and it is 39% smaller than the fp16 file (3.17 GiB vs 5.21 GiB) with the causal-3D encoder left unquantized. The pruned **DiT** int8_convrot file has not been exercised against the same path; for the DiT, use the fp8-scaled or bf16 repacks.
- **Keyframes do not set the canvas.** The released pipeline derives height and width from the first keyframe's aspect ratio when they are unset; here the configured resolution always wins and the keyframe is fitted onto it.
- **The MLP is row-chunked by default, and every chunked projection prepares its weight once.** Each block's SwiGLU MLP runs in `ceil(2·ffn_dim / hidden_size)` row-chunks (6 for H3, never below 4,096 rows; a sequence that short is not chunked), so the `fc1` output is never larger than one hidden-state tensor and the MLP's peak stays under attention's. `place_dit_for_sequence` then reserves the larger of the attention phase and the chunked-MLP phase instead of their sum: 112 KiB less per token, 4.25 GiB at 39.8k rows and 11.0 GiB at 103k before the 15% margin, which goes to keeping more of the DiT resident. A quantized `fc1` on the dequant path adds its flat transient on top of either phase, 0.57 GiB before the margin. Every op in the MLP is per-row, so chunking changes no math: on CPU the output is bit-identical, and on GPU it differs only if a chunk's row count makes cuBLAS pick a different GEMM kernel. The `ffn_chunking` pipe setting turns it off and restores the full-length MLP and its old reserve. `seq_chunk_rows` additionally chunks the qkv projection, RMSNorm/RoPE and `out_proj`, and sets the MLP's chunk too when it is the smaller of the two. When it is 0 and the activation reserve does not fit even with the DiT fully streamed, `place_dit_for_sequence` turns it on by itself (unless sparse attention or the VDN branch is on): it splits the sequence into 2, 4, 8… equal chunks and takes the fewest that fit. If the first sampling forward still runs out of memory, the OOM guard retries with the chunk halved, down to 1,024 rows, before streaming the DiT and before giving up. Chunked, the attention phase holds q, k, v, the attention output and the `out_proj` result full-length (6 widths of `inner_dim` per token, with the block input) plus one chunk of the unchunked prep; unchunked it is 11 widths. For the 9.4 s 1088×2048 clip (145,793 + 754 tokens) that is 14.36 GB instead of 25.61 GB, so 11.74 GB free holds about 7.3 s (175 frames) at that size. A quantized (fp8 or int8) `qkv_proj`, `out_proj`, `fc1` or `fc2` prepares its dequantized weight (or, with the opt-in fp8 GEMM gate, its staged fp8 weight) once per call and shares it across that call's chunks, and a runtime LoRA delta stays on the activation side of every chunk exactly as it does unchunked, so chunking never materialises a weight-sized delta. The reuse is unavailable whenever streaming layer prefetch is on (the backend's `native_stream_prefetch` setting, Admin → Backends → *backend* → Optimizations → Memory → "Prefetch streamed layers"): the prefetcher owns every streamed leaf through its own forward pre/post hooks, and a hooked leaf is deliberately sent down the ordinary per-chunk dispatch so those hooks still fire, so under prefetch a streamed projection pays one preparation per chunk. A row-masked LoRA rides a forward hook too and takes the same per-chunk path.
- **GPU validation is pending.** No end-to-end run on real weights has been performed for this family — everything above describes the implemented contract, not a measured result.

## Hardware

**No local weight files exist and no GPU run has ever been performed for this family** (`docs/native-engine.md`: "GPU validation pending; no local weight files"). The DiT alone is a 20B-parameter pruned checkpoint or a 33B full checkpoint (per this page's front matter); with a separate Qwen3-VL-32B (trimmed) text encoder, a video VAE, and an audio VAE all loaded as four independent files, this is the heaviest family PotionUI documents by a wide margin. There is no supportable tier recommendation — **not recommended on any card size** until real-weight validation exists, and separately, the weights themselves carry a territorial license restriction (excludes the EU, UK, US, and South Korea).

## FastH3 (distilled 8-step)

FastVideo's FastH3 8-Step V2 ([FastVideo/FastVideo-FastH3-Comfy](https://huggingface.co/FastVideo/FastVideo-FastH3-Comfy) on Hugging Face) is a DMD2 distillation of the same 50-block packed-sequence arch and 17-layer token refiner this page describes, trained to converge in exactly 8 steps. It ships as its own preset, `content/presets/marketplace/MiniMax-H3-Fast`, alongside the base family's preset rather than as a variant of it — the checkpoint has one fixed speed profile, not a range to pick from, and its `fl2va`-shaped repack has no reference (`ref2va`) partition, so the preset offers `video` mode only.

**Files.** The DiT is the only component that differs from the base family — the text encoder, video VAE and audio VAE are the exact same files the base preset uses. Two DiT repacks are published, both under `diffusion_models/` in the FastVideo repo: `fastvideo_fasth3_8step_v2_pruned_int8_convrot.safetensors` (22.13 GB, int8_tensorwise weights with a ConvRot rotation, the same dequant path this engine already runs for the quantized video VAE — see "`int8_convrot` is supported for the video VAE" above, now also proven for the DiT) and `fastvideo_fasth3_8step_v2_pruned_bf16.safetensors` (44.08 GB). Both are `pruned`-shape checkpoints — `adaln_t_table`, no `time_embedder` — exactly like the base family's own pruned repacks, and detection/loading needs no family-specific code beyond the one structural addition below.

**The VSA gate.** Both FastH3 files carry one key the base checkpoints do not: `blocks.N.attn.to_gate_compress.weight`, a `[inner_dim, hidden_size]` projection with no bias, present on every one of the 50 main blocks and absent from the token refiner. This is Video Sparse Attention's (VSA) coarse-attention gate — FastVideo trained FastH3 with a block-sparse attention pattern (roughly 80% sparse: a coarse routing pass decides, per query, which ~20%-by-volume set of key blocks to keep, tiled over 3D space-time cubes rather than the 1D token blocks Sol-Attn/SLA route over) and `to_gate_compress` is the linear layer that produces the routing signal. The arch module (`arch/minimax_h3/model.py`'s `MiniMaxH3Attention`) builds and loads this projection whenever the detector sees the key (`gate_compress` on `MiniMaxH3Config`), so a FastH3 checkpoint's full key set is satisfied and nothing is silently dropped at load — but no forward path reads it yet. VSA's own coarse gate plus 3D cube tiling is a genuinely different routing scheme from both `sol` and `sla` (see "Sampling" above) and porting it is separate, not-yet-done work; until then `to_gate_compress` sits loaded and inert.

**Settings.** Per FastVideo's own published recipe: steps fixed at 8 for generation (the `distilled` speed profile; the preset also declares `custom`, which only Refine faces offers, so its 4-step recipe stays editable); video stream sigma shift 10 (the audio stream keeps the base family's 3.0 — FastVideo's tutorial only respecifies the video shift); sampler `res_multistep` with the `simple` scheduler; resolution capped at a 768px short edge (768×1344 at 16:9, and siblings), narrower than the base preset's 768–1344 range; clip length still the `17n + 5` lattice at a fixed 24 fps. In place of the real VSA routing, the preset's Advanced tab defaults `sparse_attn` to `sla` at `sla_sparsity: 0.9` with `sparse_attn_start_percent: 0.2` — SLA's own top-k block routing, warmed up dense through the first ~20% of the schedule before switching on (`sparse_attn_start_percent`, wired through `is_dense_step` in `pipes/generator/video_minimax_h3/main.py`, mirrors ComfyUI's own `start_percent` and composes with the existing `sparse_attn_dense_last_steps` tail: a step runs dense if it falls in *either* window). This approximates the ~10%-keep pattern FastH3 was trained toward closely enough to be a reasonable default, but it is SLA's 1D token-block routing standing in for VSA's real 3D cube routing, not a port of it — dense (`sparse_attn: off`) is always a safe fallback when the approximation looks soft.

**What is lost relative to the base checkpoint.** No `ref2va` partition — FastVideo has not published a reference-conditioned distillation, so `MiniMax-H3-Fast` has no `refs` mode. Distillation trades some motion and audio fidelity for the 3×-fewer-steps speedup, same tradeoff as the base family's own turbo profile/LoRA, just baked into a dedicated checkpoint rather than offered as a knob. The same MiniMax H3 Community License and its territorial exclusion (EU, UK, US, Republic of Korea, covering outputs as well as weights — see "Limitations" above) apply to this distillation as they do to the base weights it derives from.

GPU validation for this checkpoint is pending, same as the rest of the family.
